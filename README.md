# AI 视频轻量需求 PRD Hub

GitHub 仓库：https://github.com/xuqiang97/ai-video-prd-hub

本仓库用于统一沉淀 AI 视频项目中不需要单独建立 HTML 原型仓库的轻量需求 PRD。

## 核心原则

每个需求最终只维护一份正式 PRD：

```text
prd/YYYY-MM/M-禅道号-英文短名/README.md
```

该 `README.md` 是需求唯一正式的范围、规则和验收来源，同时用于 GitHub 沉淀、研发实施、测试验收、钉钉流程和后续 AI 复用。

不创建钉钉版、GitHub 实施版、精简版、月份汇总版或模板副本。根目录 `README.md` 只维护一个需求索引，不创建月份 README 或第二层索引。

特殊情况下，内容本身不构成独立需求，但属于某个需求的长期复用资料，且放入主 PRD 会明显影响可读性时，经用户明确确认后，可以在对应需求的 `docs/` 下维护下级辅助文档。辅助文档不是第二份 PRD，不单独维护禅道、PRD 版本、修改纪要、调研纪要、验收标准或根目录索引；正式范围、规则和验收仍以该需求的 `README.md` 为准。

## 仓库定位与适用边界

适合放入本仓库的轻量需求包括：

- 视频生成模型或服务商配置；
- 文生视频、图生视频、首尾帧、参考视频等生成规则；
- 视频时长、比例、分辨率、帧率、音频等参数规则；
- 视频生成任务状态、异步回调和结果解析；
- 接口字段新增、调整和兼容扩展；
- 视频文件、封面、任务和业务对象之间的数据关联；
- 视频下载、转码、存储、同步及元数据处理；
- 配额、计费、失败处理和状态流转；
- AI 合成内容标识、水印或其他平台合规处理；
- 页面无明显变化的轻量前端逻辑；
- 线上问题修复及其他无需页面原型确认的轻量需求。

以上仅是需求分类示例，不代表任何需求默认需要实现这些能力，也不能直接作为未经确认的业务规则。具体需求必须根据实际资料、现网行为和用户确认逐项确定。

判断需求是否进入本 Hub 的核心标准是：

> 本需求是否需要先通过页面原型确认交互和展示效果。

如果需求涉及播放器、时间轴、镜头编辑、素材编排、参数面板重构、复杂弹窗、列表交互、生成过程展示、整体页面改版或其他明显可见的页面与交互设计，应单独建立原型仓库，通过以下方式独立交付：

```text
HTML 原型 + 唯一 README.md PRD
```

不得为了方便把明显需要原型确认的需求强行放入本 Hub。判断标准不是“前端还是后端”，而是是否需要通过可操作原型确认交互和展示效果。

## 仓库结构

```text
ai-video-prd-hub/
├── README.md
├── AGENTS.md
└── prd/                              # 首个正式需求落地时创建
    └── YYYY-MM/
        └── M-禅道号-英文短名/
            ├── README.md
            └── docs/                 # 可选，仅在用户明确确认后创建
                └── 英文短名.md
```

- 根目录 `README.md`：仓库说明和唯一需求索引。
- 根目录 `AGENTS.md`：指导 ChatGPT、Codex 等 AI 判断、编写、复核和发布需求 PRD。
- 需求目录下的 `README.md`：该需求唯一正式 PRD。
- 可选的 `docs/`：只存放经确认的下级辅助资料，不得拆分或重复维护正式需求范围。
- Git 无法保存空目录，因此在首个正式需求落地前不创建空的 `prd/YYYY-MM/` 目录，也不使用占位文件。

## 下级辅助文档

下级辅助文档只用于承载与某个需求直接相关、需要长期复用，但不适合继续扩充主 PRD 的资料，例如完整数据链路、接口字段映射、现状基线或操作说明。

使用要求：

- 默认不创建，只有用户明确确认文档定位和维护必要性后才可创建。
- 统一放在对应需求目录的 `docs/` 下，使用小写英文和中划线命名。
- 必须由父级正式 PRD 明确说明用途并直接展示完整 GitHub URL。
- 文档开头写明自身完整 GitHub URL、归属需求、父级正式 PRD 完整 GitHub URL 和文档定位。
- 本期正式范围、需要研发实现的规则和验收口径必须在父级 `README.md` 中形成结论，不得只写在辅助文档中形成隐藏需求。
- 不单独进入根目录需求索引；与父级 `README.md` 冲突时，以父级 `README.md` 为准。

## 新需求工作流程

1. 完整阅读根目录 `README.md` 和 `AGENTS.md`。
2. 判断需求是否适合本 Hub、是否应拆分、是否需要 HTML 原型。
3. 梳理资料、现网事实和缺失业务规则，在聊天中完成讨论与澄清。
4. 等用户提供正式需求名称、禅道编号和完整禅道链接。
5. 用户明确说“可以落地”后，才在本地创建或修改正式需求文件。
6. 每个正式需求只生成一份 `README.md` PRD；新增需求时同步更新根目录唯一需求索引。
7. 完成全盘语义复核，并向用户提供可直接打开的本地 PRD 供检查。
8. 只有用户再次明确说“可以发布”或“提交发布 GitHub”后，才提交、推送、创建 PR 或合并。
9. 发布后验证本地 `main`、`origin/main` 和 GitHub 文件内容一致，且本地工作区干净。

“可以落地”和“可以发布”是两个独立确认节点：

- “可以落地”只授权创建或修改本地文档，不授权任何 GitHub 写入。
- “可以发布”或“提交发布 GitHub”才授权提交和发布本次已复核的范围。
- 已发布 PRD 的后续修改也必须重新经历本地复核和新的发布确认。

同一个 Hub 可以同时讨论多个需求，但涉及根目录索引修改和 GitHub 发布时，应逐个需求处理，避免并行修改造成索引或发布范围冲突。

默认不创建 `TEMP` 目录。没有正式需求名称和禅道信息时，只继续讨论和整理；只有用户明确要求提前落库时，才创建临时内容并说明后续正式化方式。

## 原需求更新、新需求与独立迭代

以下情况直接更新原需求 `README.md`：

- 同一个禅道需求尚未进入独立开发，继续补充或修正需求；
- 评审前调整范围、规则、字段或验收口径；
- 研发或测试针对原需求提出澄清，本质仍是同一实施范围；
- 修改内容没有形成独立开发、测试或上线对象。

以下情况应新建需求目录和 `README.md`：

- 已有新的独立禅道需求；
- 原需求已经上线，本次属于后续迭代；
- 新增内容可以独立开发、测试或上线；
- 本次存在新的需求边界和验收标准；
- 线上问题被单独转为修复需求。

同一批次中的轻量顺带优化，只有在业务目标相关、由同一批研发实现且无需独立测试或上线时，才可放入同一需求，并分别写清范围和验收。能够独立实施或具有独立业务目标时应拆分。

新需求依赖历史需求时，在唯一正式 PRD 中增加“关联需求与参考资料”，直接展示相关完整禅道 URL、GitHub URL 或其他完整资料地址。

## 正式目录命名

正式需求目录统一使用：

```text
M-禅道号-英文短名
```

例如仅表示格式、不代表真实需求：

```text
M-xxxxx-video-task-status
```

命名要求：

- 英文短名使用小写字母和中划线；
- 建议控制在 3～6 个单词以内，准确描述需求核心；
- 不使用无意义的 `update`、`change`、`optimize` 单独命名；
- 默认等待正式禅道号确定后直接创建正式目录。

## 钉钉兼容与完整 URL

每份正式 PRD 及需要复制到钉钉的下级辅助 Markdown 文档，都以钉钉稳定兼容为最高优先级：

- 使用一级至三级标题、普通段落、简单列表、简单表格和必要的代码块；
- 不使用提示块、HTML、复杂嵌套或标题与加粗、链接混合的装饰性样式；
- 正式 PRD 开头直接展示完整禅道 URL，并在下一行直接展示自身完整 GitHub URL；
- 需要从钉钉打开的其他禅道、GitHub 或外部资料，也直接展示完整 URL；
- 不使用只在仓库内有效的相对地址替代需要复制到钉钉的完整 URL，不把关键地址只隐藏在 Markdown 链接文字中；
- 父级 PRD 与下级辅助文档相互引用时，双方均直接展示完整 GitHub URL。

## 需求索引

新需求按正式 PRD 创建日期倒序添加，最新需求放在最上方。项目开发、测试和上线状态以禅道为准，本索引不重复维护。当前仓库尚无正式需求。

| 日期 | 需求编号 | 业务端 | 需求名称 | 需求类型 | PRD |
|---|---|---|---|---|---|

业务端按实际影响范围填写；需求类型可根据实际情况使用 `配置`、`接口`、`规则`、`修复`、`缓存`、`数据` 或 `其他`，不得为了填表虚构信息。

## 给 ChatGPT / Codex 的使用方式

为每个 AI 视频需求建立独立对话，并把工作目录指向本仓库。建议使用以下开场说明：

```text
请先完整阅读本仓库根目录 README.md 和 AGENTS.md。根据我提供的实际资料，先判断需求是否适合本 Hub、是否应拆分、是否需要 HTML 原型，并梳理缺失业务规则。等我提供正式需求名称、禅道编号和完整禅道链接，并明确说“可以落地”后，才创建或修改本地正式需求文件。完成全盘复核后把本地 PRD 提供给我检查；只有我再次明确说“可以发布”或“提交发布 GitHub”后，才能提交和发布。
```

历史 PRD、截图和附件只作为事实参考；当前需求的正式规则以本次对话明确确认的内容为准。不得根据历史资料或通用经验自行补全视频业务规则。
